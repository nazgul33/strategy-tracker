# Cut-loss, editable sim drafts, cost-as-percent, cached bars — design

Date: 2026-11-16 · Status: draft, pending operator approval

## Intent

Four changes, driven by one need: **the market is volatile and the operator wants
to cap the loss a single bucket can take, and to experiment with where that cap
belongs.**

1. **Cut-loss (per run).** A per-run cut-loss percent. Every morning, each `held`
   bucket gets a stop-market sell at `buyPrice × (1 − cutLoss)` alongside its
   usual limit-on-close target sell. Configurable at run creation and editable
   afterwards. The simulator honours it.
2. **Editable sim drafts.** A sim becomes a *draft* when first run. Its
   configuration is visible and editable on the sim detail page, directly under
   the ticker. **Apply** recomputes the draft in place; **Save** finalizes it into
   the append-only history; **Discard** deletes it. This is what makes
   "experiment with an option to limit loss" cheap.
3. **Cost as percent.** The web shows and accepts the per-side cost as a percent
   with 3 decimals instead of raw ppm, and a new `.env` variable supplies the
   default (unset → `0.07`).
4. **Daily bars cached in the database.** Full OHLC is persisted per
   (ticker, trade date) and only genuinely missing dates are fetched from the
   provider. Less traffic, and a repeated sim over the same range costs nothing.

## Goals

- Cap per-bucket downside with a real order the operator can place at the broker,
  visible in the digest and the order table, and matchable when its fill arrives
  by screenshot capture.
- Make parameter sweeps in the simulator a matter of edit → Apply, not re-filling
  a form, and keep the saved sim history free of throwaway attempts.
- Keep percent the only unit the operator ever types or reads.
- Make a repeated sim over an already-fetched range issue **zero** provider
  requests, without ever serving a stale or partial bar.

## Non-goals

- No trailing stops, no stop-limit (the stop is market-on-trigger), no per-bucket
  override of the run-level percent.
- No stop on `force_sell` (max-age) buckets — those already exit at market.
- No cut-loss in the Telegram bot's command surface; digest rendering only.
- No sim *name* persistence. `sim_runs` still has no `name` column and the form's
  name field keeps feeding only the in-memory `Run`. Out of scope here.
- No change to `costPpm` editability on an existing run (still create-time only).
- No change to fee math, pool math, the legacy sell-target formula, or the
  `bucketBudgetCents` hard-coded `/10`.
- No sim comparison view, chart, or aggregate endpoint.
- No intraday bars, no second market-data provider, no backfill job. The cache
  fills on demand only.

## Anti-goals

Things that would make this a failure even if it shipped:

- A stop fill that books to the wrong bucket, or leaves a phantom open target
  sell in the order table after the bucket is gone.
- Sim results that silently disagree with what `computeOrders` would plan live.
- A draft that can be mistaken for saved history, or a saved sim that can be
  mutated.
- Any user-facing ppm value left in the web UI.
- A cache that serves today's half-formed bar, or that re-queries the same empty
  gap forever.

## Constraints

- Money is bigint myriadths (`1 USD = 10_000n`); cost and gaps are integer ppm.
  Never float. (`@st/core/money`)
- `packages/*` must not import `apps/*`.
- All user-facing copy in both `apps/web/src/i18n/en.json` and `ko.json`;
  `catalog.test.ts` pins identical, sorted key sets and placeholder parity, and
  forbids CJK in `ko` values.
- No source file over ~300 lines.
- `fetch` stays injectable.
- Migrations are generated by `bun run --cwd apps/server db:generate`, never
  hand-written, and apply at startup.

## Approaches

Four decisions were weighed with the operator; the chosen option is marked.

### A. How the stop order is represented

- **A fourth order kind, `stop_sell`. ← chosen.** Threaded through
  `OrderKind`, the `orders.kind` MySQL enum, booking's fill-matching chain, the
  digest, and the web badges.
- *Overload `market_sell` with a non-zero `limit_price`.* Rejected: the digest and
  order table could no longer distinguish a cut-loss from a max-age forced exit,
  and booking's `market_sell` branch already matches while ignoring price, so a
  cut-loss fill and a forced-exit fill would be indistinguishable at booking time.
- *Advisory only — display the level, place no order.* Rejected: a real stop fill
  would have no order row to match, so booking would fall through to its
  "lowest non-empty bucket with enough shares" guess.

### B. Where draft sims live

- **A `draft` flag on `sim_runs`. ← chosen.** One table, one boolean, one
  migration. `GET /api/sim/:id` is unchanged, Apply recomputes in place (same id,
  same URL), Save flips the flag. "Append-only" becomes: *finalized rows are never
  mutated or deleted.*
- *Separate `sim_drafts` + `sim_draft_days` tables.* Rejected: structurally
  stronger but duplicates the schema and the repo surface, and the detail page
  would have to read from either.
- *No persistence; the browser holds the preview.* Rejected: multi-megabyte JSON
  for a multi-year range, a second engine code path, and a reload loses the draft.

### C. Cost unit

- **Keep `cost_ppm` as storage and wire format; convert at the web boundary. ←
  chosen.** Percent with 3 decimals in the UI (`0.070 %` ⇄ `700` ppm), mirroring
  how `buyGapPpm`/`sellGapPpm` already work via `apps/web/src/gaps.ts`.
- *Migrate the column to a decimal percent.* Rejected: a migration of live data and
  a float in the money path, for no behavioural gain.

### D. Bar cache

- **Extend the existing `price_history` table to full OHLC, plus a coverage table.
  ← chosen.** `price_history` is already described in `schema.ts` as a
  (ticker, trade_date) cache that the morning pipeline backfills; it just happens
  to hold only `close`. Adding `open`/`high`/`low` keeps one table, and
  `GET /runs/:id/price-history` keeps working untouched.
- *A separate `daily_bars` table.* Rejected: two tables holding the same closes
  for the same keys, two backfill paths, and an inevitable disagreement between
  them.
- *In-memory LRU in the server process.* Rejected: loses everything on restart and
  does nothing for the first sweep of a range; the DB cache supersedes it.
- *Infer missing dates from the NYSE calendar alone, with no coverage table.*
  Rejected: outside `NYSE_YEARS` (2025–2027) `dayInfo()` degrades to
  weekends-only, so unknown holidays, pre-IPO dates, and provider gaps would look
  permanently missing and be re-queried on every single Apply — the exact traffic
  this is meant to remove.

## Design — 1. Cut-loss

### Formula

New pure helper in `@st/strategies` (`packages/strategies/src/mean-reversion.ts`),
exported for tests, next to `buyLimit`/`sellLimit`:

```
stopPrice(buyPrice, cutLossPpm):
  cutLossPpm === 0 -> null                                     // feature off
  else             -> floorCents(buyPrice * (MILLION - ppm) / MILLION)
```

`floorCents` (already in `@st/core/money`) rounds **down**, which makes the stop
marginally more protective and matches `sellLimit`'s truncation. `cutLossPpm`
of `1_000_000` (100 %) yields `0n`; treat that as off-by-degenerate — validation
caps the field below (see below), so it cannot occur.

### `computeOrders`

In the `held` loop, after pushing the `sell_loc`, push a `stop_sell` for the same
bucket when `stopPrice(...)` is non-null:

```ts
orders.push({ kind: 'stop_sell', bucketIndex: b.index, limitPrice: stop, shares: b.shares, ageDays: state.ages[b.index] ?? 0 })
```

`limitPrice` carries the **trigger** price (the order itself is market-on-trigger).
Reusing the field avoids a schema change beyond the enum and keeps every existing
consumer's price rendering correct. `force_sell` buckets get no stop. Ordering
within `DayPlan.orders` is: buy, then per held bucket `sell_loc` followed by its
`stop_sell`, then `market_sell` — so the digest reads naturally per bucket.

`computeOrders` reads the percent off the `Run`, not `MrParams`, exactly like the
gaps. `MrParams` is untouched.

**Day order, re-placed every morning** (operator ruling 2026-11-16). The stop is
emitted fresh each trading day for every held bucket, exactly like the target
sell, and yesterday's row rolls to `stale` through the existing `rollStale`. This
keeps `computeOrders` pure — it never consults existing orders — and keeps the
digest's imperative voice ("place this") uniform across all order kinds. The
operator places a day stop at the broker each morning; a stop left standing
overnight is therefore not something the tracker models.

### Domain & storage

- `packages/core/src/domain.ts`: `OrderKind` gains `'stop_sell'`; `Run` gains
  `cutLossPpm: number`.
- `apps/server/src/db/schema.ts`:
  - `orders.kind` enum gains `'stop_sell'`.
  - `strategyRuns` gains `cutLossPpm: int('cut_loss_ppm').notNull().default(0)`.
  - `simRuns` gains the same column.
- One migration, `0007_*.sql`, generated by `db:generate`, carrying every schema
  change in this design: the `orders.kind` enum `MODIFY COLUMN`; `cut_loss_ppm` on
  `strategy_runs` and `sim_runs`; `draft` on `sim_runs`; `open`/`high`/`low` on
  `price_history`; `CREATE TABLE bar_coverage`. Shape precedents:
  `0003_late_la_nuit.sql` (ADD COLUMNs), `0002_parallel_hellfire_club.sql`
  (data `UPDATE` beside a DDL change).
- `repos.ts`: `runRepo.create` takes `cutLossPpm?: number`; `updateGaps` becomes
  `updateOrderShaping(runId, { buyGapPpm, sellGapPpm, cutLossPpm })` (rename, same
  single `UPDATE`); `simRepo.insertRun` takes `cutLossPpm`.

### Validation

`cutLossPpm` is **integer ppm, a multiple of 1 000** (one decimal percent) in
`[0, 500_000]` — 0 = off, max 50 %. Lives beside `isValidPpm` in
`apps/server/src/domain/ppm.ts` as `isValidCutLossPpm`. Enforcing the granularity
server-side guarantees the one-decimal UI round-trips losslessly; the 50 % cap
keeps a fat-fingered `99.9` from being indistinguishable from a market sell.

### API

- `POST /runs` — optional `cutLossPpm`, default 0, `400 {error:'invalid cutLossPpm'}`.
- `POST /runs/:id/gaps` — body gains **optional** `cutLossPpm`. Present ⇒ validated
  and written; absent ⇒ left unchanged (keeps existing callers and tests green).
  Still `204`, still allowed in any run status.
- `GET /runs`, `GET /runs/:id` — rows carry `cutLossPpm`.

### Booking a stop fill

`apps/server/src/domain/booking.ts`, sell path. Before cut-loss the chain was:
an open `sell_loc` with **exact** `limitPrice === price`, then an open
`market_sell` for the date ignoring price, then the fallback (lowest non-empty
bucket with enough shares).

A naive "stop whose trigger ≥ fill price" rule would hijack ordinary target-sell
fills: a LOC sell prints at the close, not at the limit, so the exact match misses
routinely, and the loosest (highest) trigger in the book would then swallow the
fill. Within one bucket the target test (`price >= limit`) and the stop test
(`price <= trigger`) are disjoint, but across buckets both can admit the same fill.
The rule below (as amended 2026-11-22, see the end of this section) decides which
order, and so which bucket, a sell fill belongs to. It lives in
`apps/server/src/domain/sell-match.ts`.

- **Pool.** Orders of this run dated on the fill's trade date, of a sell-side kind
  (`sell_loc`, `stop_sell`, `market_sell`), with status `open` or `stale`. `filled`
  and `cancelled` orders never take part. A `stale` order is one whose day ended
  without a booked fill, which is what a late-captured fill is.
- **Gate.** A pool order passes when its bucket is not `empty` and holds at least
  `fill.shares`.
- **Admissible.** A gated order that fits the price: `sell_loc` when
  `price >= limitPrice`, `stop_sell` when `price <= limitPrice` (the trigger),
  `market_sell` at any price.

The rungs, first hit wins:

| # | Rung | Candidates | Pick |
|---|---|---|---|
| 1 | Exact price | the **open** `sell_loc` orders of the pool with `price === limitPrice` (a stale one never takes this rung) | among those whose bucket passes the gate, the one sized like the fill (`shares === fill.shares`) when exactly one is, else the lowest `bucketIdx`; none passes the gate: the lowest bucket's leg anyway, so the booking fails loudly |
| 2 | Share count | only when rung 1 found no exact-price leg at all: the admissible orders of every kind, open or stale | the one with `shares === fill.shares`, when exactly one is; none or several: next rung |
| 3 | Nearest price | admissible `sell_loc` and `stop_sell`, together | smallest `abs(price - limitPrice)`; on an equal distance `sell_loc` before `stop_sell`, then the lowest `bucketIdx` |
| 4 | Market sell | admissible `market_sell` | lowest `bucketIdx` |
| 5 | Fallback | no order matched | the lowest non-empty bucket with enough shares, no order flipped; none: `no-bucket-for-sell` |

Rung 1 reads the exact-price legs through the gate only to choose among them: an
exact-price print whose bucket cannot cover it still matches and fails as
`too-many-shares` (or `bucket-not-held`) in `applySellFill` instead of landing in
another bucket and pulling that bucket's legs. A stale leg never takes rung 1,
because on a bucket emptied since it would throw for a fill that belongs elsewhere.

- **Attribution.** The admissible orders on buckets other than the chosen one:
  price legs in rung-3 order, then market sells by bucket. When that list is not
  empty and the leg was chosen by rung 1, 3 or 4, the match carries an attribution
  with the rule that decided (`price` for rungs 1 and 3, `market` for rung 4). A
  rung-2 pick and the fallback carry none.
- **Flip.** The matched order flips to `filled` only when the fill empties its
  bucket; a partial fill leaves it as it was (`open` or `stale`), so the rest of
  that leg stays a candidate. An emptying fill also cancels every other `open`
  sell-side order of that bucket (see "Sibling cancel").
- **Forced bucket.** With an operator-chosen bucket the rungs are skipped; see
  "Bucket override".

For any single bucket `trigger < buyPrice < sellLimit`, so rung 3's two tests
(`price >= limit` and `price <= trigger`) can never both admit the same bucket.
Across buckets they can, and rung 3 therefore ranks target and stop legs together
by price distance instead of giving every target precedence over every stop. Rung 3
is new behaviour for fills that have nothing to do with cut-loss, and it is a
strict improvement: those fills used to miss the exact-price rung and land in the
"lowest non-empty bucket" guess.

**Amended 2026-11-18 (#43).** The original chain tried the **highest** qualifying
`sell_loc` (`price >= limitPrice`) before any `stop_sell`, on the argument that a
fill at or above some bucket's target is always a target fill. That holds inside
one bucket but not across buckets. Bucket 0 bought at 100.00 (target 103.00, stop
97.00) and bucket 9 bought at 88.00 (target 91.00, stop 85.40). Bucket 0's stop
fills at 96.50. The old chain admitted bucket 9's 91.00 target because
96.50 >= 91.00 and booked the fill there, although bucket 0's 97.00 stop is only
0.50 away and bucket 9's target 5.50. The sell was booked to the wrong bucket, and
the sibling cancel then pulled that bucket's orders. The nearest-leg rung (then
1b, rung 3 of the table above) picks the leg nearest to the fill price, which books
this fill to bucket 0's stop.

**Amended 2026-11-22 (#52 to #55, #57).** Five changes to the rule, each from a
ruling of the follow-up decisions log:

- **#52, share count (ruling 1).** At a normal exit several targets fill at one
  close and price distance cannot tell them apart: a fill landed in the wrong
  bucket and a later fill failed `no-bucket-for-sell`. A full-leg fill's share
  count equals its order's size, so rung 2 uses it. This reverses the 2026-11-18
  "price distance only" ruling. The exact-price rung stays first (controller
  ruling): an exact print is the strongest signal, and an exact-price print its
  bucket cannot cover must still fail loudly instead of booking elsewhere. Cost:
  a partial fill whose share count equals another bucket's leg size is booked
  there without a notice; in particular a second partial of a leg can be booked to
  another bucket whose leg size equals the shares left. Still open, tracked as #74.
- **#53, stale legs (ruling 2).** A fill captured for an earlier day and confirmed
  after the morning re-plan found that day's legs `stale`, fell to the fallback,
  and the sibling cancel pulled the wrong bucket's legs for today. A `stale` leg
  dated on the fill's trade date is now in the pool, behind the shares gate. This
  reverses the pinned test "a stale stop order never matches".
- **#54, partial fills (ruling 3).** The first partial fill flipped its order to
  `filled`, so the rest of that leg stopped being a candidate and booked to another
  bucket. The order now flips only when the fill empties its bucket. A partially
  filled order therefore stays `open`; the next morning it is rolled to `stale` like
  any unfilled order and counts in the digest's "{count} unconfirmed orders from
  {date}" warning, so a day with a partial reports one more order than before. The
  re-plan sizes the next day's legs from the bucket's remaining shares, as before.
- **#55, market alternatives (ruling 4).** `market_sell` legs on other buckets are
  listed in the attribution notice (new copy with no limit or distance), after the
  price legs, and take part in rung 2. Ranking by price is unchanged otherwise: a
  any admissible price leg still beats a market sell, at any distance, when the
  share count does not decide.
- **#57, bucket override (ruling 5).** The operator can book a sell to a bucket of
  their choice (see "Bucket override").

- **Tie-break.** An open target at exactly the fill price comes first: among those
  that can cover the fill, the one sized like the fill, else the lowest bucket; if
  none can cover it, the lowest one is returned and the booking fails loudly. Then
  the share count (rung 2, only when no exact-price target exists). Then price
  distance. Kind (target before stop) and then bucket index break exact distance
  ties only.
- **Attribution notice.** Sent when a leg on *another* bucket was also admissible
  and the leg was chosen by the exact-price rung, by price distance or by the
  market-sell rung; never when the share count decided (controller ruling: a normal
  multi-target exit sends none, where it would otherwise send one per fill but the
  last). A fill booked to an operator-chosen bucket, or to the fallback bucket,
  sends no attribution notice. The notice names the rule that decided. It is one
  `notifications` row (Notifications tab) and one Telegram message per allowed
  chat; with no allowed chats one row with chat id `web` is written (shown as
  "web only" in the Notifications tab) and nothing is sent; the sibling-cancel
  notice does the same. They are sent after the run lock is released and before
  any sibling-cancel message. The alternatives are listed price legs first
  (nearest first), then market-sell legs by bucket. The copy keys in
  `packages/telegram/src/i18n.ts` are `sell-attributed`, `sell-attributed-alt`,
  `sell-attributed-alt-market`, `sell-attributed-why-price`,
  `sell-attributed-why-market`, `leg-sell_loc`, `leg-stop_sell` and
  `leg-market_sell`. The notice for a deleted buy (see "Sibling cancel") adds
  `buy-removed-cancelled` and `buy-removed-cancelled-market`; the latter drops the
  limit, like `sibling-cancelled-market`.

**Known limitations (whole-branch review, 2026-11-20; every item is addressed; orders that were cancelled are never reopened, see "Sibling cancel"):**

1. Addressed 2026-11-22 (#54): a partial fill no longer flips its order, so the rest of that leg stays a candidate.
2. Addressed 2026-11-22 (#55): `market_sell` legs on other buckets are listed as alternatives and take part in the share-count rung; price ranking is unchanged.
3. Addressed 2026-11-22 (#53): a stale leg of the fill's day is a candidate; a late fill that still falls to the fallback pulls that bucket's legs for today only when it empties the fallback bucket.
4. Addressed 2026-11-22 (#52): the share-count rung separates same-close targets of different sizes.
5. Addressed 2026-11-23 (#73): a fill edit, an applied correction or a delete that empties a bucket retires that bucket's sell legs through the same rule as a new fill.

**Sibling cancel.** Both legs sit live at the broker, so when one fires the other
must stop looking live in the tracker *and* the operator must pull it by hand.

- A sell that **empties its bucket**, whichever leg, rung, fallback or forced
  bucket booked it, cancels every other `open` sell-side order (`sell_loc`,
  `stop_sell`, `market_sell`) of that run and bucket dated on or after the fill's
  trade date (`tradeDate >= filledOn`) with `cancelReason: 'broker-filled'`
  (already in `CANCEL_REASONS`); the matched order is not among them, it flips to
  `filled`. A fill captured for an earlier day and confirmed after the morning
  re-plan therefore also cancels **today's** freshly planned legs.
- The bucket's `stale` sell-side orders dated exactly on the fill's trade date are
  cancelled too (same reason), without a message: that broker day is over and
  nothing is live to pull. Otherwise, once the bucket is bought again, such a leg
  would pass the shares gate on the new lot and could absorb a later late fill of
  that day.
- A **partial** fill cancels nothing — the remaining shares still need both legs,
  and the next morning's plan re-sizes them. It leaves the matched order as it was
  (`open` or `stale`) until a fill empties the bucket (ruling 3).
- The cancel happens inside the same `withRunLock` span, after the fill insert,
  alongside the `order.setStatus('filled')` flip (made only when the fill empties
  the bucket), preserving the R15 "flip the order last" ordering.
- **It notifies** (operator ruling 2026-11-16): a `notifications` row plus a
  Telegram message, reusing the `order-cancelled` path that `POST
  /runs/:id/orders/:orderId/cancel` already uses (`runs.ts:258`), with new en/ko
  copy naming the leg that fired and the leg to pull. The send is fire-and-forget
  *outside* the lock span so a Telegram outage can never fail a booking.
- **An edit or a correction that empties a bucket** (2026-11-23, #73) retires the
  legs the same way. `rebookFillUnlocked` compares the state before and after the
  replay; if the edited fill's bucket was not `empty` before and is `empty` after,
  and its newest fill by id in the edited history is a sell, it takes that sell as
  the emptying one. Its leg
  is the order `matchForcedLeg` picks for it (none: nothing flips); that leg
  flips to `filled`, and the same cancels apply: every other `open` sell-side order
  of the bucket dated on or after the sell's trade date with `broker-filled`, the
  bucket's `stale` ones dated on the sell's trade date silently. The same
  `sibling-cancelled` notice goes out, after the lock is released and with no
  attribution. An edit that leaves the bucket held, or an applied correction (it
  changes price and fee, never shares), touches no order. A different bucket that
  the rebuild empties because the stored state had drifted from the fill history
  is repaired without touching its orders, on edit, delete and recalc alike. The orders are read
  before the first write, so a failing read fails the edit (or the delete below)
  with nothing stored and a retry can repeat it. A failing order write propagates
  after the edit is stored: the bucket's legs may be partly retired, and the run's
  orders then need a manual check. Only a notifier failure is swallowed.
- **A delete that empties a bucket** (2026-11-23, #73) deletes the bucket's buy,
  the only way `deleteFillUnlocked` empties one. Nothing flips: no sell happened.
  Every `open` sell-side order of the bucket dated on or after the deleted buy's
  trade date is cancelled with reason `other` and announced with the
  `buy-removed-cancelled` notice (the buy it was placed for was deleted). The
  bucket's `stale` sell-side orders from that date on are cancelled with `other`
  without a notice: they belong to a lot that no longer exists, and a later rebuy
  of the bucket must not let one pass the shares gate and absorb a late fill. The
  rule is `retireLegs` in `apps/server/src/domain/retire-legs.ts`, the one place
  that retires sell legs for a new fill, an edit and a delete.
- **Orders are never reopened.** When an edit or a delete makes a bucket held
  again (a sell edited down, a deleted sell), the legs a sibling cancel or this rule
  cancelled stay cancelled; the bucket has no live protection until the next
  morning's plan places its legs again.

`rollStale` needs no change (it is kind-agnostic).

### Bucket override (#57, ruling 5)

The operator can book a sell to a bucket of their choice when the matching rule
cannot know which bucket really sold.

- **Fields.** An optional `bucketIdx` on the manual fill body (`POST
  /runs/:id/fills`) and on the pending confirm `overrides` (`POST
  /pending/:id/confirm`). It applies to a sell only; absent or `null` means
  automatic. No new column: the fill's `bucket_idx` already records where it went,
  and whether the bucket was forced is not recorded.
- **Validation.** `bookUnlocked` throws `invalid-bucket` before any read that leads
  to a write when `bucketIdx` is given and the side is not `sell`, or it is not a
  non-negative integer. The rest is the ordinary sell validation in
  `applySellFill`: `bucket-not-found` (past the run's bucket count),
  `bucket-not-held` (empty) and `too-many-shares`. All four answer `422 { error }`
  on both routes, and nothing is persisted: no fill, no ledger row, no order flip,
  and a pending row stays pending.
- **Leg choice.** The rungs are skipped. `matchForcedLeg` picks, among that
  bucket's pool orders (sell-side, `open` or `stale` on the fill day) that fit the
  price: exactly one with `shares === fill.shares`, else the nearest price leg
  (target before stop on a tie), else a `market_sell`; none fits: nothing flips.
  There is no gate; the bucket's own validation is `applySellFill`'s. The leg flips
  and the bucket's other open sell-side legs are cancelled only when the fill
  empties the bucket, as for any sell.
- **No notice.** A sell booked to an operator-chosen bucket sends no attribution
  notice: the operator made the choice. The sibling-cancel notice still goes out.
- **`GET /api/pending`.** Each row carries `heldBuckets: { index, shares }[]`: the
  buckets of that row's own run whose state is not `empty` (force-sell buckets hold
  shares and are included), ascending by index, read once per distinct run;
  `[]` when the run no longer exists.
- **Web.** The manual fill dialog (add mode) and each pending row, when the side is
  `sell`, show a **Bucket** selector (`BucketSelect`): "Automatic" (the default, no
  `bucketIdx` is sent) and one option per held bucket ("Bucket N · S sh"). A buy
  never sends `bucketIdx`. A bucket chosen on a pending row is not a vision
  correction: it does not open the keep/discard screenshot prompt and is not
  written to the vision review record.

### Raising cut-loss on buckets that are already underwater

Turning cut-loss on, or tightening it, can put the new trigger **above** the
current market for buckets already down — those stops fire at the next open, in
one batch. That is what a cut-loss means, so the design **warns, does not block**
(operator ruling 2026-11-16):

- `EditRunModal` shows, before save, how many of the run's held buckets would sit
  at or below the proposed trigger as of the run's latest known close
  (`price_history`), with en/ko copy. The save button still works.

## Design — 2. Cut-loss in the simulator

`resolveDay` in `apps/server/src/sim/sim.ts` gains a `stop_sell` pass, placed
**after `market_sell` and before `sell_loc`**:

```
for each stop_sell (ascending bucketIndex):
  if bar.open <= trigger   -> fill at bar.open     // gapped through
  else if bar.low <= trigger -> fill at trigger     // touched intraday
  else                       -> no fill
```

Operator ruling (2026-11-16): the **intraday low triggers**, not just the open.
A gap-down open fills at the open (worse than the trigger, as in reality); an
intraday touch fills exactly at the trigger, ignoring slippage.

**Same-day conflict rule:** if a bucket's target (`high >= sellLimit`) and its
stop (`low <= trigger`) are both reachable on the same bar, the **stop wins** —
the daily bar carries no intraday path, and attributing the loss is the
conservative reading. Because the stop pass runs first, the later `sell_loc` pass
finds the bucket empty and `applySellFill` throws into the existing
"not filled" `catch`. This is a documented, deliberate pessimism, written as a
comment at the stop pass.

That silence is itself a hazard — in the replay it would look identical to "the
high never reached the target". So when the stop pass has emptied a bucket whose
`sell_loc` was also reachable (`bar.high >= its limit`), the `sell_loc` pass emits
`{ type: 'skipped', bucketIndex, reason: 'stop-preempted' }`. `SimReplay` renders
it through the existing `reasonKey('simSkip', reason)` convention with new en/ko
copy, so the day says out loud that the stop took the bucket from the target.

`SimInput` gains `cutLossPpm?: number` (validated with `isValidCutLossPpm`,
default 0) and the synthetic `Run` carries it, so the replay plans exactly what
production would. The forced exit at the last bar's open is unaffected.
`sim_runs.cut_loss_ppm` persists it.

## Design — 3. Sim drafts

### Schema

`simRuns` gains `draft: boolean('draft').notNull().default(true)` — new rows are
drafts; existing rows migrate to `false` (the generated migration's `DEFAULT true`
applies only to inserts, so the migration must also `UPDATE sim_runs SET draft = 0`
for pre-existing rows; drizzle-kit will not emit that, so it is appended by hand to
the generated `0007` file, the one hand-edit this design allows, precedent
`0002_parallel_hellfire_club.sql`).

### API

| Method | Path | Behaviour |
|---|---|---|
| `POST` | `/api/sim` | unchanged shape; the created row is a **draft**. `{ id, dayCount }` |
| `PUT` | `/api/sim/:id` | **Apply.** Same body as `POST` minus `ticker`. Re-runs, replaces the draft's `sim_days`, updates its config columns. `{ id, dayCount }`. `409 {error:'sim-finalized'}` if not a draft, `404` if unknown |
| `POST` | `/api/sim/:id/save` | **Save.** `draft → false`. `204`. `409 {error:'sim-finalized'}` if already saved, `404` if unknown |
| `DELETE` | `/api/sim/:id` | **Discard.** Deletes the row and its days. Drafts only; `409 {error:'sim-finalized'}` on a saved sim |
| `GET` | `/api/sim` | now returns **all** rows, each with `draft: boolean`, newest first |
| `GET` | `/api/sim/:id` | unchanged, `run` DTO gains `draft` |

The ticker is the draft's identity and is **not** editable; changing ticker means
starting a new sim. Everything else is: `from`, `to`, `poolCents`, `costPpm`,
`buyGapPpm`, `sellGapPpm`, `cutLossPpm`, `params.bucketCount`, `params.maxAgeDays`.
`PUT` reuses the exact `validateBody` path as `POST` (ticker taken from the stored
row), so validation can never diverge between the two.

`PUT` and `DELETE` do their reads and writes in a transaction (or delete-then-insert
guarded by the same connection) so a failed re-run cannot leave a draft with a
half-replaced day set.

Apply goes through the cached bar reader (design 5), so a sweep over an unchanged
date range issues no provider requests at all.

`SimRepoSurface` gains `rewriteDraft` (one guarded call that swaps the config and the
day set together, so no caller can replace days on a saved run), `finalize`,
`deleteRun`, and `sweepDrafts(olderThan)`.

### Draft lifecycle

- **Sweep:** at startup, `main.ts` deletes drafts whose `created_at` is older than
  7 days (plus their `sim_days`), logging the count. Single-operator tool; no cron
  needed. The constant lives beside the other wiring in `main.ts`.
- Saved sims are never mutated or deleted by any code path.

### Web

`SimRun.tsx` is a 37-line shell today and must stay under ~300 lines, so the
config panel is a new component: `apps/web/src/components/forms/SimConfigPanel.tsx`.

```
Simulation #12  (draft)                        [ Save ]  [ Discard ]
AAPL
┌──────────────────────────────────────────────────────────────────┐
│ Start [2025-01-02]  End [2026-11-14]   Pool (USD) [100000.00]    │
│ Cost (%) [0.070]  Buy gap (%) [0.5]  Sell gap (%) [1.0]          │
│ Cut loss (%) [3.5]  Buckets [10]  Max age [20]        [ Apply ]  │
└──────────────────────────────────────────────────────────────────┘

```

- The panel sits between the ticker line and `SimReplay`, pre-filled from the run
  DTO + `paramsJson` (reusing `SimReplay`'s existing tolerant `parseParams`, which
  moves into a shared module so both can import it).
- **Apply** validates with the same rules as the `Sim.tsx` form (so that validation
  moves into a shared `apps/web/src/simconfig.ts` used by both), `PUT`s, then
  refetches the detail. Busy state on the button; the replay keeps showing the old
  days until the new ones arrive. The day index resets to the last day, which
  `SimReplay`'s existing `useEffect` on `total` already does.
- **Save** → `POST .../save`, then the badge flips to saved and the panel becomes
  read-only (same fields, disabled, no Apply/Save/Discard).
- **Discard** → confirm dialog (existing `dialog.*` pattern) → `DELETE` → navigate
  to `#/sim`.
- For a **finalized** sim the panel renders read-only. This also replaces the
  config fragment currently crammed into `SimReplay`'s nav meta line (ticker, pool,
  max age, gaps) — that span is removed, since the panel above now shows all of it.
- `Sim.tsx` list: a **Drafts** card above the saved-sims table, same columns plus a
  per-row discard; drafts are excluded from the saved table. Reuses the existing
  `TableWrap`/`EmptyNote` patterns.
- `api.ts` gains `updateSimRun`, `saveSimRun`, `deleteSimRun`; `SimRunDto` gains
  `draft`.

## Design — 4. Cost as percent, and its default

- `parseEnv` (`apps/server/src/wire/deps.ts`) gains `defaultCostPpm: number`, read
  from `DEFAULT_COST_PERCENT`. Unset/blank → `0.07` → `700`. Parsed as a
  **percent string with up to 3 decimals**; anything malformed joins the existing
  `missing`-style startup failure with a clear message naming the variable.
  `.env.example` gains `DEFAULT_COST_PERCENT=0.07` with a one-line comment.
- `HttpDeps.defaultSettings` gains `defaultCostPpm`; `GET /api/settings` returns it.
  It is **read-only** — not settable through `PUT /settings` (env-owned, like the
  vision defaults' fallback role).
- `POST /runs` and `POST`/`PUT /api/sim`: `costPpm` becomes **optional**, defaulting
  to `deps.defaultSettings.defaultCostPpm`. When supplied it must be an integer
  `>= 0` **and a multiple of 10** (0.001 % granularity) so the 3-decimal UI
  round-trips losslessly. Existing stored values (200) already satisfy this.
- Web: every cost input becomes **Cost (%)**, 3 decimals, prefilled from
  `getSettings().defaultCostPpm` (replacing the hardcoded `'200'` in
  `CreateRunForm` and `Sim.tsx`). Every cost *display* renders percent —
  `RunsList`/`Sim.tsx` already use `bpPercent(costPpm / 100)`, which is the same
  number; the change is to label it as a percent and to show 3 decimals
  consistently via a new `costPercentText(ppm)` in `format.ts`.
- i18n: `runCostPpm` / `simCostPpm` values become "Cost (%)" / "수수료 (%)"; keys
  keep their names (they are referenced from several places) and gain a hint key.

## Design — 5. Cached daily bars

### Schema

- `price_history` gains `open`, `high`, `low` as **nullable** bigints. Legacy rows
  (close-only, written by the morning pipeline's `persistClose`) keep NULLs and
  stay valid for `GET /runs/:id/price-history`, which reads `close` only.
- New `bar_coverage` table: `id`, `ticker`, `fromDate`, `toDate` — the date ranges
  that have actually been fetched from the provider, with an index on `ticker`.
  Coverage, not row presence, is what makes "missing" decidable: a holiday the
  committed NYSE table doesn't know about, a pre-IPO date, or a provider gap has
  no row and never will, and without coverage it would be re-queried on every
  Apply.

### Reader

New module `apps/server/src/market/bars.ts`, wired in `main.ts` as the
`fetchDailyBars` that `HttpDeps` and the sim already take — so every existing
injection point and every test fake keeps working unchanged, and
`packages/market-data` stays DB-free.

```
cachedFetchDailyBars(ticker, from, to):
  today    = todayEt()
  horizon  = min(to, last fully closed session before today)
  gaps     = [from, horizon] minus merged coverage rows for ticker
  for each gap (merged into contiguous sub-ranges, widest first):
      bars = upstream fetchDailyBars(ticker, gap.from, gap.to)
      upsert bars into price_history (full OHLC)
      insert coverage row, merging with any adjacent/overlapping row
  if to > horizon: fetch (horizon, to] fresh every time, do NOT cache or cover it
  return price_history rows in [from, to] that have full OHLC, ascending
```

- **Never cache an unfinished session.** Anything at or after today (ET) is
  fetched live on every call and neither upserted with OHLC nor covered, so a
  half-formed bar can't be frozen into history. The existing close-only
  `persistClose` write is unaffected.
- Ticker keys are normalized through the existing `normTicker` (`repos.ts:11`)
  so the cache cannot fragment.
- `MarketDataError` from the upstream fetch propagates unchanged — a partially
  filled gap keeps whatever rows and coverage it already committed, so the next
  attempt resumes rather than restarting.
- Coverage rows are merged on write (adjacent or overlapping ranges collapse),
  keeping the row count bounded for a ticker swept repeatedly.
- `fetchLastClose` (used by the morning pipeline) is untouched: one request for
  one number, already persisted by `persistClose`.
- `GET /runs/:id/price-history`'s own backfill (`runs.ts:152-162`) switches to the
  cached reader, so the chart and the sim share one cache and one upsert path.
