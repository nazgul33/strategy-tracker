# Migrations

Generated by drizzle-kit (`bun run db:generate`). Applied at startup via `applyMigrations(db)` (drizzle migrator) pointed at `apps/server/db/migrations`. Paths resolve relative to process cwd; run from repo root in dev.

## Before deploying the `mr_` split (migrations 0013–0015)

Follow these steps in order.

1. **Why.** These migrations rename ten tables to `mr_*`, move five columns from `strategy_runs` into the new `mr_runs` table, and then drop them from `strategy_runs`. The migration cannot be rolled back; the dump taken below is the only way back.

2. **Precondition.** Production must already have migrations 0000–0012 recorded:

   ```bash
   docker exec mariadb_st_prod sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" "$MARIADB_DATABASE" -e "SELECT COUNT(*) FROM __drizzle_migrations"'
   ```

   It must print 13. If it prints fewer, deploy the last pre-split version first and confirm it boots: migrations 0010–0012 are not re-runnable, so they must not share a boot with this change.

3. **Stop the app first**, so nothing is booked between the dump and the deploy:

   ```bash
   docker stop stratagy_tracker_prod
   ```

4. **Dump to a path outside the repository** (the file holds trading records, screenshots and the vision API key):

   ```bash
   docker exec mariadb_st_prod sh -c 'exec mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" --single-transaction "$MARIADB_DATABASE"' > ~/st_db-before-mr-split.sql
   ```

   Then check that it finished: `tail -n 1 ~/st_db-before-mr-split.sql` must start with `-- Dump completed on`. A failed dump still leaves a file behind.

5. **Rehearse on a copy (recommended).** Start a throwaway `mariadb:11.4` container and load the dump into it. Record `SELECT id, pool_cents, buy_gap_ppm, sell_gap_ppm, cut_loss_ppm, MD5(state_json) FROM strategy_runs ORDER BY id` and the `COUNT(*)` of the ten tables. Apply migrations only (no server, so no bot or cron touches the copy), from the repo root:

   ```bash
   DATABASE_URL=mysql://... bun -e "import {getDb,applyMigrations,closeDb} from './apps/server/src/db/client'; const d=await getDb(process.env.DATABASE_URL); await applyMigrations(d); await closeDb()"
   ```

   Compare the same values from `mr_runs` (`run_id` for `id`) and the counts of the `mr_*` tables. Run the command a second time and confirm nothing changes, then remove the container. This also proves the dump restores.

6. **Deploy** with `prod_helpers/run_prod_container.sh`.

7. **Post-check.** `SELECT COUNT(*) FROM __drizzle_migrations` prints 16, and `SELECT (SELECT COUNT(*) FROM strategy_runs) = (SELECT COUNT(*) FROM mr_runs)` prints 1.

8. **If the server dies during the migration,** start it again; it continues where it stopped. Every statement is safe to run twice, and the copy into `mr_runs` and the column drop live in separate files.

9. **To go back,** stop the app; drop and recreate the database (or drop all eleven `mr_*` tables, including `mr_runs`), load the dump, and start the previous image. Loading the dump over a migrated database leaves the `mr_*` tables in place, and the next boot of the new version then fails on the rename. Never start an older image on a partly or fully migrated database.

After this change reaches `main`, the first DB-gated test run or dev-server start migrates `st_test`, so any checkout on an older commit must be rebased or have `st_test` recreated.
